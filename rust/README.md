# Rust workspace

Opt-in Rust code for everything that is not inference. ggml and `src/` stay in C/C++ and are consumed through `include/llama.h`.

Crates:

- `llama-sys`: bindgen bindings for `llama.h`, `ggml.h`, `ggml-backend.h`, `ggml-cpu.h`, `gguf.h` and the C shim `common/rust-shim/llama_ext_c.h`, committed in `llama-sys/src/bindings.rs`
- `llama`: safe wrapper (backend, model, vocab)
- `llama-http`: HTTP transport for `llama-server` (hyper + tokio), an rlib with a C ABI (`llama-http/include/llama_http.h`)
- `llama-schema`: JSON schema to GBNF grammar (`llama-schema/include/llama_schema.h`), used by `json_schema_to_grammar` in `common/json-schema-to-grammar.cpp`; `build_grammar` still uses the C++ converter
- `llama-quantize-core`: the pure part of `llama-quantize` (argument parsing, ftype table, legacy imatrix reader, imatrix normalization and filters, KV overrides); no FFI, so `cargo test -p llama-quantize-core` needs no C++ build
- `llama-quantize`: `llama_rs_quantize` (the whole `llama-quantize` tool) and the imatrix loader that `tools/imatrix` reads through `llama_imatrix_load`, over `llama.h` and `gguf.h` (`llama-quantize/include/llama_quantize.h`)
- `llama-sampling`: the reasoning-budget sampler behind `common_reasoning_budget_*` and, with the `llguidance` feature, the llguidance sampler behind `llama_sampler_init_llg` (`llama-sampling/include/llama_sampling.h`); both are `llama_sampler_i` vtables over `llama.h`
- `llama-args`: the `Params` struct (port of `common_params`, `llama-args/src/params.rs`) for the `common/arg.cpp` port; today it only round-trips `common_params` (`llama-args/include/llama_args.h`)
- `llama-rs`: the single static library C++ links (`llama-rs/include/llama_rs.h`). It re-exports the C ABI of every Rust piece (`llama-http` today) so the process carries one copy of `std`; with shared libs `libllama-common` owns it (whole-archive) and everything else resolves the symbols through it
- `tools/tokenize`: port of `tools/tokenize/tokenize.cpp` (`llama-tokenize`)
- `tools/gguf-split`: port of `tools/gguf-split/gguf-split.cpp` (`llama-gguf-split`)

`llama-tokenize` covers `-m`, `-p`, `-f`, `-e/--no-escape`, `--stdin`, `--ids`, `--no-bos`, `--no-parse-special` and `--show-count`, and its output matches the C++ tool byte for byte. The model download flags (`-hf`, `-mu`, `-dr`, `--offline`) and the generic common flags (`--log-*`, `-v`, `--color`) need the `common/` port and are not implemented yet.

`common/rust-shim` wraps `src/llama-ext.h`. That header has C++ linkage and C++ types, so Rust cannot link it directly.

## Build

Requires a Unix target. The bindings are generated ahead of time, so a normal build does not run bindgen or need libclang. `llama-sys/build.rs` stores a hash of every header the bindings were generated from and fails the build when one of them changes; regenerate with `cargo build -p llama-sys --features bindgen` (needs libclang) and commit `llama-sys/src/bindings.rs`.

```sh
cmake -B build-rust -DLLAMA_RUST=ON
cmake --build build-rust
```

`cargo` runs from the `llama-rust` CMake target and links against the libraries in `build-rust/bin`. Non-Debug builds use the cargo profile `cmake` (release with incremental compilation, `rust/Cargo.toml`), so editing Rust and rebuilding takes seconds; pass `-DLLAMA_RUST_CARGO_PROFILE=release` for a fully optimized build, for example when packaging. CMake also defaults `CMAKE_LINK_DEPENDS_NO_SHARED` to ON, so a change in `libllama-common` does not relink every executable. To run cargo by hand, build the C++ side first and point `LLAMA_LIB_DIR` at the libraries:

```sh
cd rust
LLAMA_LIB_DIR=../build-rust/bin cargo test
```

The default `LLAMA_LIB_DIR` is `build-rust/bin`.

`llama-gguf-split` supports `--split`, `--merge`, `--split-max-tensors`, `--split-max-size`, `--no-tensor-first-split`, `--dry-run` and `--delete-splits`. Split files, merged output, stdout/stderr and exit codes match the C++ tool byte for byte. Deviations: `--version` prints only the libllama version (build commit/compiler live in `common/`), `--split-max-tensors 0` is an error instead of a division by zero, and a short read from the input is an error instead of silently writing garbage.

`llama-schema` replaces the body of `json_schema_to_grammar(const common_json &, bool)` in `common/json-schema-to-grammar.cpp`: the schema goes in as JSON text and the grammar or the error message comes out, so the C++ signature, the llguidance branch and the `invalid_argument` contract are unchanged. `build_grammar(cb)`, `common_chat_schema` and `common/trie.cpp` stay in C++ because the PEG and chat parsers consume them (they move with 3.5/3.6). The converter is a line-by-line port, including nlohmann's number formatting (Grisu2, table generated by `scripts/rust-golden/gen_grisu_table.py`), key order (`serde_json` with `preserve_order`) and `std::stoi` semantics. Deliberate deviations, all in inputs where C++ misbehaves: a nesting limit of 256 turns the stack overflow (or endless loop) that `allOf` + `$ref` cycles cause in C++ into an error, and a limit of 512 nested schemas while reading the schema (each `$ref` hop counts) does the same for long `$ref` chains, so a chain of more than about 128 `$ref`s fails with `schema nesting too deep` both ways; regex patterns are read per character, so `é+` quantifies the whole character instead of its last byte; JSON nested deeper than 128 levels is rejected by `serde_json`. Oracles: `tests/test-json-schema-to-grammar.cpp`, `test-json-schema.cpp` and `test-grammar-integration.cpp` pass unchanged with the flag ON; `llama-schema/tests/golden/cases.json` holds the 81 cases of the first one (`scripts/rust-golden/schema_cases.py`); `scripts/rust-golden/schema_fuzz.py` + `schema_driver.cpp` + `schema_diff.py` run the same random schemas through a build with the flag OFF and ON and compare grammar, error text and warnings (45k schemas, no difference except the three deviations above).

`llama-http` is the transport of `server_http_context` (`tools/server/server-http.cpp`); handlers, scheduler and sampling stay in C++. The cpp-httplib server transport is gone. It covers routing, CORS, API keys, the ready gate, multipart, streaming with cancellation on client disconnect, unix sockets, `SO_REUSEPORT` and the embedded UI assets and `--path` static directories (files, `index.html`, 301 for directories, `ETag` + `If-None-Match`; no range requests or compression). `--ssl-cert-file` / `--ssl-key-file` serve HTTPS with rustls (`ring` provider, TLS 1.2 and 1.3, ALPN `http/1.1`, handshake per connection with a timeout); CMake always enables the `llama-http/tls` cargo feature, so HTTPS does not depend on OpenSSL. Giving only one of the two files is an error, whereas cpp-httplib silently serves plain HTTP. Read timeouts cover the request head and write timeouts close a connection whose peer stops reading (a stalled write, not total response time). A leftover unix socket file is removed at startup only if nothing accepts connections on it. Each request runs its handler on a tokio blocking thread; the runtime itself has a fixed small worker count. Header names are written in title case to match cpp-httplib, except `ETag`, which becomes `Etag`.

`llama-quantize` replaced `tools/quantize/quantize.cpp` and `common/imatrix-loader.cpp`, and both files are gone: `tools/quantize/main.cpp` and `app/llama.cpp` call `llama_rs_quantize`, and `tools/imatrix/imatrix.cpp` reads the `llama_imatrix_view` from `llama_imatrix_load` directly. Oracle: `scripts/rust-golden/quantize_diff.py` runs 63 `llama-quantize` argument combinations (ftypes by name and number, output naming, `--keep-split`, `--imatrix` in both formats with include/exclude filters, tensor types, pruning, KV overrides, errors and usage, `LLAMA_TRACE`) and compares exit code, stdout, the tool's own stderr lines and the sha256 of every output file with `quantize_golden.json`, recorded from the C++ tools. It also runs `llama-imatrix --in-file` to convert dat to gguf and back, re-save and merge the two fixtures, plus two load errors, comparing exit code and output files; that covers the Rust loader as `tools/imatrix` uses it. ctest runs it as `test-quantize-golden` (label `main`; it downloads the 1 MB stories260K model on first run). The imatrix fixtures live in `scripts/rust-golden/quantize/`. The C++ tool and the Rust port also produced identical full logs, libllama output included, and `llama-imatrix --in-file` gives the same statistics and output. The goldens were recorded on x86_64; other targets may quantize to different bytes. Deviations, all on malformed input: a legacy imatrix with a negative name length is an error (C++ reads out of bounds), and a non-imatrix file with a huge length field fails without allocating that many bytes first.

`llama-sampling` replaced `common/reasoning-budget.cpp`, and the file is gone: `common/sampling.cpp` flattens the token sequences and calls `llama_rs_reasoning_budget_*` from `llama_sampling.h`, which also holds the state enum, and `common/log.cpp` installs the trace sink, so the `COM_TRC` lines are unchanged. The state machine and its Aho-Corasick matcher are a line-by-line port. Oracle: `tests/test-reasoning-budget.cpp` (12 state-machine cases, clone, manual force, end match) runs against the C API through a small flattening helper.

With `-DLLAMA_LLGUIDANCE=ON`, CMake enables the cargo feature `llama-rs/llguidance`: `llama-sampling` depends on the `llguidance` crate (pinned to 1.0.1, the version the removed `ExternalProject` cloned) and calls its `ffi` functions directly, so the llguidance sampler and its tokenizer cache are Rust and `common/llguidance.cpp` only forwards. The build no longer clones the llguidance repository or links a second static Rust library with its own copy of `std`. Dependencies of the crate resolve through `rust/Cargo.lock` instead of llguidance's own lock file. Oracle: `tests/test-grammar-llguidance.cpp` passes unchanged.

The server test suite (`tools/server/tests`, `LLAMA_SERVER_BIN_PATH=build-rust/bin/llama-server`) is the oracle for this crate. The harness gives xdist workers ports `8080 + 10 * n`, so run it with `PORT=<free port>` and without `-n` if 8080 is taken.

`llama-args` holds `Params`, the Rust side of `common_params`, for the port of `common/arg.cpp` (Phase 4). The C++ code keeps `common_params` as a data struct and crosses the boundary as CBOR: `common/params-serde.cpp` encodes and decodes it with field names, so a field missing or added on either side is an error instead of a silent shift. Strings are byte strings (prompts read from files need not be UTF-8) and floats keep `inf` and NaN. Devices and buffer types cross by name and are resolved again in C++; callbacks and `llama_context`/LoRA pointers do not cross. The field-by-field C++ code (`common/params-serde.inc`) and the oracle dump (`scripts/rust-golden/params_dump.inc`) are generated from the clang AST of `common/common.h` by `scripts/gen-common-params.py` (`--check` reports stale output); the Rust structs are maintained by hand. Oracle: `scripts/rust-golden/params_diff.py` replays 1884 parse cases recorded from the C++ parser (ctest `test-params-golden`), and `params_driver` round-trips every parsed `common_params` through Rust and back, failing the case if any field changes.
